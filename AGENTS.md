# Инструкции для работы с проектом

## Контекст проекта

- Перед изменениями прочитай [сводку истории чата](docs/chat-summary.md) и [README.md](README.md). Новые пожелания пользователя имеют приоритет над прежними решениями.
- Текущий результат — минималистичный лендинг с отдельными описаниями услуг. Исходный макет Figma служит источником контента; текущий дизайн сайта утверждён в последующей переписке и отличается от макета.

## Подключение Figma

- Используй официальный плагин Figma и его MCP-инструменты. Не путай подключение Figma к агенту с разработкой собственного плагина внутри Figma.
- Если инструментов Figma нет, сначала найди официальный Figma через `plugin-management` → `search_plugins`. Для подключения используй карточку найденного плагина; если требуется действие пользователя, укажи конкретный шаг. Не утверждай, что подключение состоялось, пока оно не проверено.
- Установка в приложении Codex: **Plugins → Figma → Install Figma**, затем авторизация в нужном аккаунте Figma и **Allow access**. Если плагин уже подключён, повторная установка не нужна. Названия пунктов могут меняться — сверяйся с [официальной инструкцией Figma](https://developers.figma.com/docs/figma-mcp-server/remote-server-installation/).
- Для клиента с ручной настройкой MCP официальный удалённый сервер: `https://mcp.figma.com/mcp`; используется HTTP и авторизация Figma. Этот путь сам по себе не устанавливает навыки Figma. Предпочитай готовый плагин, который включает сервер и навыки. Для удалённого подключения приложение Figma Desktop не требуется.
- Проверяй подключение через `whoami`, когда нужно подтвердить аккаунт или разобраться с правами и лимитами. Не сохраняй email аккаунта, токены или ответы авторизации в репозиторий. Установка плагина, доступ к файлу и тариф/место Figma — отдельные вещи; факт оплаты не подтверждает доступ ко всем инструментам.

## Работа с макетом Figma

- Исходный файл: [«Саблина Ника»](https://www.figma.com/design/APaW5kcEMKzPKhunkZ9Bll/?node-id=0-1). `fileKey`: `APaW5kcEMKzPKhunkZ9Bll`, корневая страница `nodeId`: `0:1` (в URL записывается `0-1`).
- Перед первым чтением или редактированием файла в новой задаче создай сессию через `create_session`, если инструмент доступен; используй возвращённый `sessionId` в поддерживающих его вызовах этой задачи.
- Перед переносом дизайна прочитай доступный навык `figma-design-to-code`. При отсутствии локального навыка используй механизм чтения навыков, указанный самим инструментом. Перед записью в Figma прочитай соответствующее руководство для выбранного инструмента.
- Основной источник размеров, структуры и оформления — `get_design_context` выбранного фрейма. Для большого файла сначала получи обзор через `get_metadata`, затем читай нужные фреймы отдельно. Проверяй визуальный результат через `get_screenshot`; при необходимости получай переменные через `get_variable_defs`.
- Адаптируй примеры к существующим HTML/CSS/JavaScript. Не добавляй React, сборщик или другие зависимости только потому, что они встретились в ответе Figma.
- Сохраняй нужные изображения и SVG локально в `assets/`, поддерживай карту в `design-assets.js` и `assets/design-assets.json` для ресурсов из исходного макета. Не оставляй временные MCP-ссылки в опубликованном сайте.
- Сверяй тексты, цены, контакты и изображения с источником. Если данные не указаны, не придумывай их. При лимитах или отказе доступа сообщи точную ошибку; не обещай, что покупка определённой подписки обязательно её устранит. Актуальные условия проверяй в [документации Figma](https://developers.figma.com/docs/figma-mcp-server/).
- Запрос изменить сайт означает изменение репозитория. Записывай изменения в исходный файл Figma только по запросу пользователя. При запросе обратного переноса сайта выбери подходящий инструмент Figma и его навык, не подменяй редактируемый дизайн одним скриншотом без согласования результата.

## Git

- Каждое завершённое логическое изменение сохраняй отдельным коммитом. Это относится также к документации, настройкам и этой инструкции.
- Перед коммитом проверяй diff и выполняй подходящие для изменения проверки.
- Используй понятные сообщения коммитов, описывающие результат изменения.
- Не добавляй в Git секреты, токены, локальные файлы окружения и результаты сборки, если они не нужны для публикации.
- Не включай чужие незавершённые изменения в свой коммит и не переписывай историю без явного запроса.
- Если коммит или push заблокирован настройками автора, доступом или ошибкой, сообщи об этом пользователю; не придумывай имя или email.

## Сайт и публикация

- Репозиторий проекта: https://github.com/N6Ssa/decision_bureau.git.
- Как только начнётся разработка сайта, добавь исходники сайта в этот репозиторий и настрой публикацию через GitHub Pages.
- При выборе архитектуры учитывай совместимость с GitHub Pages, включая базовый путь `/decision_bureau/`.
- Настрой автоматическую сборку и публикацию при push в `main` через GitHub Actions, если выбранный стек требует сборки.
- После каждого завершённого изменения сайта выполняй необходимые проверки, делай коммит и отправляй изменения в GitHub, чтобы опубликованный сайт обновлялся.
- Проверяй результат публикации и сообщай пользователю адрес сайта. Не утверждай, что сайт опубликован, до успешной проверки.
- Если необходимая настройка GitHub недоступна, подготовь все файлы публикации и точно укажи оставшийся шаг.
